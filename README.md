# 두근두근 소개팅 매칭 부스

동아리 축제 부스용 MBTI 매칭 웹앱. QR을 찍고 폰으로 들어와서 질문 4개에
답하면, 같은 MBTI에 조건이 맞는 이성 참가자를 찾아 인스타 ID를 보여준다.
조건에 맞는 사람이 없으면 대기 화면으로 보낸다.

**프레임워크 없는 순수 HTML/CSS/JS + Cloud Firestore.** 빌드 과정도, 띄워둘
서버도 없다. 정적 호스팅에 올리면 끝난다.

설치는 **[SETUP.md](SETUP.md)** 를 따라가면 된다.

---

## 화면 흐름

```
1 시작  →  2 기본 정보  →  3~6 질문 4개  →  7 한마디
                                              ↓
                                        8 분석 중 (1.5초)
                                              ↓
                          9 매칭 성공  ←──┴──→  10 매칭 대기
```

제출 전까지는 뒤로가기로 앞 화면에 돌아갈 수 있고, 제출한 뒤에는 막힌다
(브라우저 뒤로가기 제스처 포함).

결과·대기 화면에는 **"다음 사람 차례 · 처음부터 다시"** 버튼이 있다. 부스에서
폰 한 대를 여러 명이 돌려 쓰기 때문이다. 누르면 localStorage를 비우고
새로고침해 시작 화면으로 돌아간다. 서버에 저장된 응답은 지우지 않으므로
**다음 사람은 다른 인스타 ID로 참여해야 한다.**

## MBTI 판정

축(EI / NS / TF / PJ)마다 문항 3개씩, 총 12문항이 들어 있다.
세션 시작 시 축별로 1개씩 랜덤으로 뽑아 4문항을 출제한다.
**뽑은 결과는 localStorage에 저장되므로 새로고침해도 같은 문항이 나온다.**

각 문항의 선택지에 MBTI 한 글자가 붙어 있고, 4개를 이어 붙이면 유형이 된다:
`EI + NS + TF + PJ` → 예: `ENFP`. AI도 가중치도 없는 결정론적 규칙이다.

## 매칭 알고리즘

### 절대 조건 — 둘 다 만족해야 후보가 된다

1. **성별이 반대**
2. **학년 희망이 양쪽 다 맞음**
   - 상대의 희망 학년에 내 학년이 있고
   - 내 희망 학년에 상대 학년이 있어야 한다

### 그다음 MBTI로 줄 세운다

위를 통과한 사람 중 **MBTI가 가장 많이 겹치는 사람**, 동점이면 랜덤 1명.

MBTI는 절대 조건이 아니다. 16종이라 완전 일치를 요구하면 후보가 0명이 되기
일쑤여서 겹치는 글자 수로 순위만 매긴다.

### 왜 학년은 절대 조건인가

참가자가 직접 고른 조건이라 어기면 불만이 나온다. "3학년만 볼래요"라고 했는데
1학년이 뜨면 매칭이 성사돼도 만족스럽지 않다. 조건을 못 맞출 바에는 대기
화면을 보여주는 편이 낫다는 판단이다.

덤으로 화면의 궁합 %가 정직해진다 — 학년이 안 섞이므로 MBTI 일치도만 뜻한다.

### 궁합 퍼센트 — MBTI만 본다

`js/config.js`의 `MBTI_PERCENT` 배열에 있다. 숫자만 고치면 된다.

| MBTI 일치 | 궁합 |
| --- | --- |
| 4글자 | 100% |
| 3글자 | 85% |
| 2글자 | 70% |
| 1글자 | 55% |
| 0글자 | 40% |

학년은 여기 **1도 안 들어간다.** 그래서 "궁합 85%"는 언제나 곧이곧대로
"MBTI 3글자 일치"를 뜻한다. 학년이 하나도 안 맞는 상대와 매칭돼도 MBTI가
완전히 같으면 100%가 뜬다 — 의도된 동작이다.

### 매칭 실패는 언제 나나

**절대 조건을 통과하는 이성이 한 명도 없을 때.** 대기 화면으로 보낸다.

행사 초반이나, 희망 학년을 하나만 고른 참가자에게 자주 난다. 부스에서
**"희망 학년을 여러 개 고르면 매칭 확률이 올라간다"**고 안내해야 한다.
화면 2의 힌트 문구에도 그렇게 적어 뒀다.

> ⚠️ **운영 주의** — 하리보를 매칭 성사자에게만 주므로, 매칭이 안 된 참가자는
> 빈손으로 돌아간다. 대기 화면 참가자용 소소한 보상을 따로 두는 것도 방법이다.

**이미 매칭된 사람도 다시 뽑힌다. 매칭 횟수 제한은 없다.** 따라서 한 사람이
여러 명과 매칭될 수 있고, 매칭은 상호 배타적이지 않다. 이건 의도된 동작이다.

쿼리는 성별 하나만 Firestore에 보낸다. 단일 필드 동등 조건이라 자동 색인으로
처리되고 복합 색인을 따로 만들 필요가 없다. 부스 규모(많아야 수백 명)에서는
전부 받아와 계산해도 충분하다.

## 중복 참여 방지

같은 인스타 ID로는 한 번만 참여할 수 있다. 기본 정보 화면에서 한 번,
제출 직전에 한 번 더 확인한다 (그 사이에 다른 기기에서 참여했을 수 있어서).

경합 조건까지 완전히 막지는 못한다 — 두 기기가 정확히 동시에 제출하면
둘 다 통과할 수 있다. 완벽히 막으려면 인스타 ID를 문서 id로 쓰고
`create` 시 존재 여부로 걸러야 하는데, 그러면 문서 id에 개인정보가 들어가
URL에 노출될 여지가 생긴다. 부스 운영 맥락에서는 현재 방식이 낫다고 봤다.

## 운영진 대시보드

`/admin/` — Firebase 이메일 로그인. 참가자·매칭 표, MBTI 분포, CSV 내려받기,
그리고 **데이터 삭제**(행별 / 매칭만 / 전체)를 할 수 있다.

> ### ⚠️ 삭제 기능을 쓰기 전에
>
> `firestore.rules`의 `isStaff()`가 현재 **"로그인했으면 운영진"** 이다.
> 이게 안전하려면 Firebase 콘솔에서 **가입이 꺼져 있어야** 한다:
>
> Authentication → Settings → 사용자 작업 → **"만들기(가입) 사용 설정" 끄기**
>
> 켜져 있으면 누구나 API로 계정을 만들 수 있다. `apiKey`는 이 저장소의
> `js/config.js`에 공개되어 있으므로, 가입이 열린 채로 삭제 규칙을 게시하면
> **아무나 가입해서 참가자 데이터를 전부 지울 수 있다.**
>
> 가입을 끌 수 없다면 `firestore.rules`의 `isStaff()` 안 주석을 풀어
> 운영진 이메일 목록 방식으로 바꾸면 된다.

## 알려진 한계

**참가자 목록 읽기가 열려 있다.** 브라우저에서 매칭을 계산하려면 다른 참가자
문서를 읽어야 한다. 즉 프로젝트 ID를 아는 사람은 참가자들의 인스타 ID를
긁어갈 수 있다. 무료 요금제에서 클라이언트 SDK만으로는 막을 수 없다
(Firestore 규칙은 문서 단위라 특정 필드만 숨기는 게 안 된다).

막으려면 매칭을 Cloud Functions로 옮기고 규칙의 `allow read`를 `false`로
바꿔야 하며, Blaze(종량제) 요금제가 필요하다. 자세한 내용은
[SETUP.md](SETUP.md#3-보안-규칙-배포--이-단계를-건너뛰면-안-됩니다) 참고.
