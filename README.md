# 두근두근 소개팅 매칭 부스

동아리 축제 부스용 MBTI 매칭 웹앱. QR을 찍고 폰으로 들어와서 질문 4개에
답하면, 같은 MBTI에 조건이 맞는 이성 참가자를 찾아 인스타 ID를 보여준다.
조건에 맞는 사람이 없으면 대기 화면으로 보낸다.

**프레임워크 없는 순수 HTML/CSS/JS + Cloud Firestore.** 빌드 과정도, 띄워둘
서버도 없다. 정적 호스팅에 올리면 끝난다.

설치는 **[SETUP.md](SETUP.md)** 를 따라가면 된다.

---

## 화면 흐름

```
1 시작  →  2 기본 정보  →  3~6 질문 4개  →  7 한마디
                                              ↓
                                        8 분석 중 (1.5초)
                                              ↓
                          9 매칭 성공  ←──┴──→  10 매칭 대기
```

제출 전까지는 뒤로가기로 앞 화면에 돌아갈 수 있고, 제출한 뒤에는 막힌다
(브라우저 뒤로가기 제스처 포함).

## MBTI 판정

축(EI / NS / TF / PJ)마다 문항 3개씩, 총 12문항이 들어 있다.
세션 시작 시 축별로 1개씩 랜덤으로 뽑아 4문항을 출제한다.
**뽑은 결과는 localStorage에 저장되므로 새로고침해도 같은 문항이 나온다.**

각 문항의 선택지에 MBTI 한 글자가 붙어 있고, 4개를 이어 붙이면 유형이 된다:
`EI + NS + TF + PJ` → 예: `ENFP`. AI도 가중치도 없는 결정론적 규칙이다
(화면에 "AI가 분석 중"이라고 뜨는 건 연출이다).

## 매칭 알고리즘

제출한 사람 기준으로 아래를 **전부** 만족하는 참가자를 찾는다:

1. 성별이 반대
2. MBTI가 동일
3. 상대의 `preferredGrades`에 내 학년이 포함
4. 내 `preferredGrades`에 상대 학년이 포함

조건을 만족하는 사람이 여럿이면 그중 **랜덤 1명**. 없으면 대기 화면.

**이미 매칭된 사람도 조건만 맞으면 다시 뽑힌다. 매칭 횟수 제한은 없다.**
따라서 한 사람이 여러 명과 매칭될 수 있고, 매칭은 상호 배타적이지 않다.
이건 의도된 동작이다.

쿼리는 조건 1~2만 Firestore에 보내고 3~4는 받아와서 거른다. 네 조건을 전부
쿼리로 보내면 복합 색인을 따로 만들어야 하는데, 색인이 없으면 쿼리 자체가
실패한다. 부스 규모(많아야 수백 명)에서 "동일 MBTI + 반대 성별"은 이미 아주
작은 집합이라 이 편이 배포 사고가 날 여지가 적다.

## 중복 참여 방지

같은 인스타 ID로는 한 번만 참여할 수 있다. 기본 정보 화면에서 한 번,
제출 직전에 한 번 더 확인한다 (그 사이에 다른 기기에서 참여했을 수 있어서).

경합 조건까지 완전히 막지는 못한다 — 두 기기가 정확히 동시에 제출하면
둘 다 통과할 수 있다. 완벽히 막으려면 인스타 ID를 문서 id로 쓰고
`create` 시 존재 여부로 걸러야 하는데, 그러면 문서 id에 개인정보가 들어가
URL에 노출될 여지가 생긴다. 부스 운영 맥락에서는 현재 방식이 낫다고 봤다.

## 알려진 한계

**참가자 목록 읽기가 열려 있다.** 브라우저에서 매칭을 계산하려면 다른 참가자
문서를 읽어야 한다. 즉 프로젝트 ID를 아는 사람은 참가자들의 인스타 ID를
긁어갈 수 있다. 무료 요금제에서 클라이언트 SDK만으로는 막을 수 없다
(Firestore 규칙은 문서 단위라 특정 필드만 숨기는 게 안 된다).

막으려면 매칭을 Cloud Functions로 옮기고 규칙의 `allow read`를 `false`로
바꿔야 하며, Blaze(종량제) 요금제가 필요하다. 자세한 내용은
[SETUP.md](SETUP.md#3-보안-규칙-배포--이-단계를-건너뛰면-안-됩니다) 참고.
